## Prova de autorização

- **RBAC negado**: os testes provam status HTTP (403/404) **e** ausência de efeito persistido, fazendo uma segunda chamada (com credencial válida do Dono) para ler o estado real depois da tentativa negada — não se limitam ao código de status (`auth-rbac.test.ts:358-385`, `:443-475`, `:521-546`).
- **Revogação**: o teste reaproveita o **mesmo** JWT já emitido para o Operador removido e prova 403 na request imediatamente seguinte à remoção, sem esperar expiração — isso demonstra que a API consulta a membership a cada request (`resolveMembershipContext` roda em uma transação nova por chamada) em vez de confiar em claim do JWT.
- **Cross-Loja**: duas Lojas sintéticas (`storeId`/`storeBId`) e dois Donos distintos provam que a membership de uma Loja não lê, não altera e não remove membership de outra Loja; a garantia é dupla — filtro explícito por `context.storeId` no código **e** RLS (`store_members_tenant_isolation`, `stores_tenant_isolation` em `packages/db/prisma/migrations/20260728130000_store_tenant_rls/migration.sql:56-74`).
- **O que não é provado neste ticket**: acesso positivo do Operador a Pedidos/status, porque a rota de Pedidos não existe ainda (ticket 08). Isso é esperado e não é lacuna do ticket 03 — a única superfície de negócio hoje (`/stores/:id`) é corretamente restrita ao Dono.
- **Runtime não privilegiado**: `assertRestrictedRuntime()` é chamado no boot (`apps/api/src/server.ts:44`, inalterado) e testado para rejeitar credencial administrativa mesmo com `SET LOCAL ROLE` rebaixado (`auth-rbac.test.ts:275-279`, inalterado), fechando o caso de a API rodar de fato como `postgres`/bypass RLS. **Rechecagem pós-ticket-04:** a checagem em si só mudou de lugar textual, não de comportamento — está agora em `packages/db/src/index.ts:94-119` dentro de `createTransactionalBusinessDatabase`, e `createBusinessDatabase.assertRestrictedRuntime` (`:222-224`) continua chamando-a dentro de um `prisma.$transaction` fresco contra a `BUSINESS_DATABASE_URL` restrita (`server.ts:17-19`, inalterado). O script novo do ticket 04 (`apps/api/scripts/preflight-production-migrations.ts:41-43,146-154`) conecta com credencial privilegiada via `createAdministrativeDatabase` **só para provar migrations pendentes em uma transação com rollback obrigatório** (`throw rollbackProof` em `:201`, nunca commitado) — ele instancia sua própria `buildApp()` local via `app.inject()` (sem bind de porta) e é chamado exclusivamente pelo job `migrate` da CI (`ci.yml:50`, `pnpm --filter @foode/api migrations:preflight`); `apps/api/package.json` mantém `"start": "node dist/server.js"` inalterado, isto é, o processo de produção nunca importa esse script nem a credencial privilegiada. Não há caminho pelo qual a API servida em produção aceite tráfego com credencial administrativa.
